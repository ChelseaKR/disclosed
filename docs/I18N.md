# Internationalization

i18n status: Applies - the seam is built, English is the only language

Reason: the site is a public-facing HTML surface, so the internationalization standard is not
N/A; a reader does not stop deserving a translated page because the underlying datasets are
English. Every graded source (College Scorecard, IPEDS) is a US federal English-language dataset,
the site's argument prose is authored in English, and the project has no release and no audience
yet. Translating the rationales badly would be worse than stating plainly that they are
English-only for now.

## What exists

The page templates in `src/disclosed/site.py` no longer hold prose. Every user-facing string is
looked up by key from a GNU gettext catalog, `src/disclosed/locales/<locale>/LC_MESSAGES/
disclosed.po`, and `disclosed site --locale` names which catalog to render from. The catalog
format is `.po` because that is what translation tooling reads, and it is parsed as text rather
than compiled to `.mo` because a binary blob in the repository is a claim nobody can review in a
diff. No dependency was added: the parser is about eighty lines in `src/disclosed/messages.py`.

**There is exactly one catalog, `en`.** The seam is real and the translations do not exist. That
is the honest state of it, and `tests/test_i18n.py` asserts the claim rather than leaving it to
prose: `messages.available()` returns `("en",)`, and the day it does not, the test is where the
claim gets updated in the same commit as the catalog.

## The rule that does not move

The five classification tokens - `reported`, `implausible`, `suppressed`, `not_applicable`,
`missing` - stay machine keys in the CSV export and its Table Schema, and are translated only at
the presentation layer. They are translated in exactly one function,
`site._classification_copy`, on the way into one page.

They are the product's contract: five different facts that a consumer joins on. A Spanish export
whose cells said `no_reportado` would not merge with an English one, and nothing in the file
would say so - the absence-rendered-as-a-value defect this project exists to name, committed by
this project, in its own published dataset.

`disclosed.dataset` therefore does not import `disclosed.messages`, and
`TestTheExportKeepsMachineKeys` in `tests/test_i18n.py` fails if it starts to. That class builds
a **pseudolocale**: a complete catalog, generated from the English one, whose every message is
wrapped in brackets. It asserts the pseudolocale actually changed the rendered page before
asserting the export is unchanged by it, because a negative control that silently fails to apply
reads as a pass.

## What a catalog has to survive before a page is rendered from it

None of these are warnings. `messages.load` raises and the build fails.

- **Complete.** Every message the site renders, present and non-empty. A page served as
  `lang="es"` with English paragraphs in it is an absence rendered as a value; nothing falls back.
- **No leftovers.** A message the site no longer renders means the translator is working from a
  page that does not exist.
- **Placeholders preserved,** per message and per plural form. A translated sentence that lost
  its `{count}` reads as a finished claim with the quantity removed.
- **A plural rule this implementation knows.** `Plural-Forms` is looked up in a table, not
  evaluated. A language whose rule is not in `_PLURAL_RULES` is refused rather than pluralised by
  the English rule.

`<html lang>` and `og:locale` are read off the catalog, so a translated page cannot claim to be
English or the reverse.

## What this fixed on the way

Six published state pages said "1 institutions". The templates had no way to express a plural, so
the catalog now does, and the singular forms are written out. That is the only prose change in
the whole conversion: the other 611 pages differ from their previous bytes only where a sentence
that used to be wrapped across source lines is now one line.

## What remains

Building the seam is not internationalising the project. Still open:

1. **No second locale.** Adding one is a translation job with a reviewer, not a code change. A
   machine translation shipped as though reviewed would be the same defect in a different place.
2. **Numbers are formatted with English conventions.** `12%`, `6,163`, `57.1%` come from Python's
   `,` and `%` format specs. Correct locale-aware numbers need CLDR data, which means either a
   dependency or a hand-maintained table, and that is its own decision.
3. **The `disclosed.ask` layer is English throughout.** Its prompts, its verifier, the federal
   definitions it quotes verbatim, and the sentences inside the page's one inline script are all
   English. Translating the frame around an English answer would make it look translated. The
   question form's own labels do come from the catalog.
4. **Field labels, rationales and statute names are not translated,** deliberately. They are the
   wording the grader applies and the wording the published Table Schema carries, and a rationale
   that read one way on the page and another in the schema would be two different rules.
